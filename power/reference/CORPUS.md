# The reference corpus, and the one thing it does not tell us

This note is for whoever goes looking for more Microsoft material. It says what we already hold, how
we use it, the single gap that matters, and what would close it.

## 1. What the corpus is

`power/reference/` holds Microsoft Learn pages pulled verbatim as markdown from
`MicrosoftDocs/powerapps-docs` and `MicrosoftDocs/power-platform`. Includes are resolved, nothing is
summarised, only the YAML frontmatter is stripped. Every page keeps its own heading, a `Source:` link
back to the live page, and the body exactly as published. The snapshot is dated 19 September 2026.

Twenty-eight files, 5,061 headings of level 1 to 3, about 448 pages. By docset, with page counts:

| Docset | Files | Pages |
| --- | --- | --- |
| Canvas apps `01` to `15` | get started 14, connect to data 30, design the interface 47, modern controls 32, classic controls 36, common properties 6, screens and app functionality 22, solutions and accessibility 20, publish and manage 18, how-to 11, wrap wizard 9, for developers 13, performance 12, Teams 46, deprecations | 316 |
| Power Fx `16` to `19` | language concepts 13, formula reference overviews 9, function reference 51 + 50 | 123 |
| PCF `01` to `02` | component framework 9, manifest schema and ALM 25 | 34 |
| Guidance `01` | coding guidelines and co-developing 11 | 11 |
| Well-Architected `01` to `04` | experience 13, reliability 12, performance 12, operational excellence 15 | 52 |
| ALM `01` | solutions and environment variables 10 | 10 |
| Data platform `01` | tables, columns and choices 7 | 7 |

`INDEX.md` is generated by `node scripts/build-reference-index.mjs`. It carries every heading with its
file and line, grouped by file, page headings on their own lines and the headings inside a page run
together beneath them. A second section lists each Power Fx page with its "Applies to" block condensed
to one string.

The lookup rule is: read the index, grep this folder for the heading, read only that section. Never
read a corpus file whole. The reason is context cost. The corpus is roughly 520,000 words; a single
whole file runs to thousands of lines. Anything learned that outlives one change is distilled into
`power/RUNBOOK.md` or `power/canvas/CONTROLS.md` in the same unit that learned it.

## 2. How we consume it

The corpus feeds four offline artefacts, not the app directly.

`scripts/yamlcheck.mjs` hands every `*.pa.yaml` to YamlDotNet's strict parser, because `pac canvas
pack` copies YAML in verbatim and a malformed file only fails when Studio opens it.

`scripts/fxcheck.mjs` binds every formula in `power/app` with Microsoft's own Power Fx compiler
against a symbol table built from `power/canvas/columns.json`, the column catalogue built from the
imported solution rather than from memory.

`tools/fxcheck/modern-controls.json` is the modern controls' property and enum table: 22 controls
under the identifier and version the YAML writes, every property with its type, and 42 enum types
declared with their members. It was hand-assembled from `canvas-apps-04-modern-controls-reference.md`
and from the instances Studio itself configured in `power/canvas/source/Src/Screen1.pa.yaml`, and the
Studio instance wins wherever the two differ.

`power/canvas/CONTROLS.md` is the verified-identifier ledger. Per control: the exact identifier with
version, the `Variant` values Studio wrote, every property name Studio saved, and what the official
page adds or contradicts. Lines are marked Studio-confirmed, documented-only, or catalogue-only.

The runbook's "Layout calibration" block is the pattern to copy: measured behaviour first, then a
"Source rules (corpus, not yet Studio-verified)" list citing corpus file and heading, for example
`guidance-01` > "Responsive design guidelines in Power Apps" > "Use auto-layout containers".

## 3. The gap

Learn documents controls by their Studio property-pane labels and describes values in prose. The YAML
source format (Power Apps canvas source code, `.pa.yaml`, produced and consumed by `pac canvas
pack`/`unpack`) uses different tokens: control identifiers with versions (`Label@2.5.1`,
`Badge@0.0.24`, `ModernButton@1.0.0`), property names (`LayoutMinWidth`, `LayoutGap`, `FillPortions`,
`LayoutJustifyContent`, `LayoutOverflowX`), enum references (`'BadgeCanvas.Appearance'.Filled`,
`ButtonAppearance.Subtle`, `'Column (Table)'.Value`), and variant tokens (`Variant: VariableHeight`,
`ManualLayout`, `AutoLayout`). No page in the corpus lists these tokens. Our only source for them has
been YAML that Studio wrote: a downloaded `.msapp` unpacked with `pac canvas unpack`, and the
`Screen1` samples in `power/canvas/source`.

Concretely. The Badge page says `Appearance` accepts filled, outline, ghost or inverted, in prose, with
no enum table; our catalogue also carries `Tint`, which is catalogue-only and unconfirmed. The
container pages say "Minimum width"; the YAML says `LayoutMinWidth`, Studio-confirmed. "Flexible
height gallery" is `Variant: VariableHeight`, known only because a Studio sample wrote it. The Header
and ModernCard title-text property names, and every Checkbox property, remain unconfirmed because
those instances were never configured.

## 4. What would close it

Things worth fetching, in order of value:

- An official schema for canvas source YAML. `pa.schema.yaml` already sits in the repo root: draft-07
  JSON Schema v3.0, covering the file shape (`App`, `Screens`, `ComponentDefinitions`, `DataSources`,
  `EditorState`, control instance names, `Control:` identifier form, `Properties` formula maps). It is
  control-agnostic. It does not list per-control properties or enum members, which is exactly the gap.
- The `microsoft/PowerApps-Language-Tooling` repo is now cloned at `power/vendor/PowerApps-Tooling`
  (shallow, 673 files, 20 September 2026). It holds the v3.0 `pa.schema.yaml`, the msapp pack and
  unpack source (`src/Persistence/MsappPacking`), `docs/YAMLFileFormat.md` and test fixtures. It
  contains no per-control property lists or enum member lists, and zero occurrences of
  `VariableHeight`, `Tint`, `FillPortions`, `LayoutMinWidth`, `ManualLayout` or `ThemeColor`. Its
  control identifier enum
  (`src/schemas/pa-yaml/v3.0/ControlLibraryVDev/ControlTypeId-1P-controls-enum.schema.yaml`) uses
  development names such as `FluentV9/Badge` that differ from the `Badge@0.0.24` and
  `ModernButton@1.0.0` tokens Studio writes, so it must not be used to correct `CONTROLS.md`. In
  short, the repo settles structure, not names; Studio-written YAML remains the only authority for
  tokens, and enum member lists are most likely to surface from Studio's formula bar autocomplete.
  The repo's unpublished control identifier enum names modern controls `FluentV9/Badge` and similar,
  and omits `ModernCard`. The live Waypoint app imports and renders with the bare tokens
  `Badge@0.0.24`, `ModernButton@1.0.0` and `ModernCard@1.3.0`, which is the Studio round trip already
  done, so the bare tokens stand and the enum is not to be used to rename anything.
- Documentation for `pac canvas`.
- Any Learn page on "canvas app source code" or the YAML code view.
- The Power Fx enum reference.
- A Fluent-to-canvas property mapping for the modern controls.
- Anything listing control library versions.

Two rules hold while reading any of it. A doc omitting a token is not evidence the token is wrong. A
Studio-written sample outranks a doc for names.

The fastest confirmation for any item in the section 5 table is not a document. Place one instance
of each unconfirmed control on a throwaway screen in Studio, set the properties in question through
the pane, save and publish; the msapp is then downloaded and unpacked with pac canvas unpack
(scripts/refresh-skeleton.mjs and the skeleton in power/canvas/source), and the YAML Studio wrote
gives the exact property tokens and the enum member it chose. Research then only needs to cover
what Studio cannot show, chiefly the full member list of each enum.
